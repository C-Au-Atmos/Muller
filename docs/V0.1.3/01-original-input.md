## Stage 7.11 生命周期共同原始约束

- 适用平台为 Windows 桌面版 Muller；只约束主窗口，不改变文件选择器、确认框等
  系统窗口或子窗口的关闭语义。
- Settings 新增“启动与关闭”分组；中英文界面均需提供完整名称、状态、错误信息、
  键盘操作和可访问名称。
- 生命周期设置在隐藏、恢复、正常退出、重新启动和应用升级后保持一致；读取失败
  不得阻止 Muller 启动。
- 隐藏窗口时沿用现有资源策略：暂停视觉与音频、取消可取消的预览，但不静默中断
  扫描或已提交的文件操作。
- Windows 注销、关机和应用更新退出不得被“隐藏到系统托盘”策略拦截。
- 最小化按钮只最小化窗口，不受关闭行为设置影响。
- 保留现有托盘、全局快捷键、工作区状态和隐藏时资源挂起能力；本版本继续使用
  `Ctrl+Shift+Space`，不增加失焦自动隐藏。

## `REQ-0.1.3-001` - 关闭主窗口行为可选

历史 ID：`MUL-LIFE-001`

### 原始描述

> 在 Settings 中选择关闭主窗口时是退出 Muller，还是仅隐藏到系统托盘。

最初反馈原文：

> 现在的muller点几右上角的×是只会关掉页面，但实际上还是会在后台运行，我需要你在设置里面加一个可选项，用于控制右上角的×是直接关闭muller进程还是仅隐藏muller界。

原文来源：`SRC-711-FEEDBACK`

来源文档进一步明确了以下用户可观察行为：

- “关闭主窗口时”提供“隐藏到系统托盘”和“退出 Muller”两个选项。
- 默认选择“隐藏到系统托盘”，保持已有使用习惯；修改成功后，从下一次关闭请求
  起立即生效，不要求重新启动。
- 右上角 `X`、`Alt+F4` 和任务栏“关闭窗口”采用同一选择。
- 选择隐藏时，主实例、托盘、全局快捷键、工作区状态和允许继续的后台任务保留。
- 选择退出时，Muller 通过正常退出流程结束；再次手动启动属于冷启动。
- 托盘“Quit Muller”始终真正退出，不受关闭行为选择影响。
- 恢复默认设置后，关闭行为恢复为“隐藏到系统托盘”。
- 本需求不新增独立的退出确认流程；若存在未保存内容保护，各正常退出入口共享
  该保护，用户取消后窗口保持可见。

## `REQ-0.1.3-002` - 当前用户登录时自动启动

历史 ID：`MUL-LIFE-002`

### 原始描述

> 在 Settings 中控制当前 Windows 用户登录后是否自动启动 Muller。

最初反馈原文：

> 添加开机自启动的可选项开关

原文来源：`SRC-711-FEEDBACK`

来源文档进一步明确了以下用户可观察行为：

- “登录 Windows 后自动启动 Muller”开关默认关闭，必须由用户主动开启。
- 只为当前 Windows 用户启用或停用，不要求管理员权限，也不影响其他用户。
- 开关操作立即生效，但开启时不额外启动进程，关闭时不结束或隐藏当前进程。
- 登录启动时 Muller 在后台保持隐藏，不弹窗、不抢焦点；只出现一个主实例和一个
  托盘图标。
- 登录启动时若 Muller 已运行，不创建第二个主实例，也不改变当前窗口状态。
- 登录启动与手动启动同时发生时只保留一个主实例，手动启动的显示意图优先。
- Settings 中的开关必须反映 Windows 实际状态；操作失败时恢复实际状态并显示
  本地化、可操作的错误信息，应用继续运行。
- 安装路径变化或升级后，已开启的自启动仍指向当前有效版本，不产生重复项；卸载
  时清理由 Muller 创建的自启动项。
- 开启自启动不等于进程守护；用户退出后，本次登录会话内不会自动重启。

## `REQ-0.1.3-003` - 单实例与桌面图标唤出

历史 ID：`MUL-LIFE-003`

### 原始描述

> Muller 已运行时，再次点击桌面图标只唤出既有界面，不创建第二个主实例。

最初反馈原文：

> 点击桌面muller图标后逻辑改为，如果没有相应进程，就打开，如果有，就把界面呼出

原文来源：`SRC-711-FEEDBACK`

来源文档进一步明确了以下用户可观察行为：

- 单实例始终启用，不提供关闭开关；每个 Windows 用户交互会话最多一个 Muller
  主实例，不同用户会话互不接管。
- 无主实例时，桌面快捷方式、开始菜单或直接运行可执行文件会创建并显示主窗口；
  已有主实例时，只唤出既有窗口，不创建第二个窗口、托盘图标或工作区。
- 已隐藏的窗口显示并激活，已最小化的窗口恢复并激活，后台可见窗口置前并激活，
  已最大化窗口保持最大化；存在可操作模态窗口时优先激活该窗口。
- 唤出不得刷新界面、重置路由或工作区、取消后台任务；当前路径、标签、选择、
  输入内容和任务状态保持不变。
- 快速双击或连续多次启动收敛到同一实例；主实例尚在启动时记住显示请求，窗口
  就绪后执行。
- 主实例异常退出后，下一次手动启动仍能正常冷启动。
- 既有实例无响应时不得静默创建第二个主实例；本版本不提供“强制重启”交互。
- Windows 限制抢焦点时，至少保证窗口可见并在任务栏提示注意；正常环境以成功
  激活为目标。

## `BUG-0.1.3-001` - 浏览模式搜索栏兼容微软拼音和微信输入法

历史 ID：`None`

### 原始描述

用户首次上报：

> 搜索输入框输入结果不正常


来源：`用户上报`

用户反馈和后续复现明确了以下可观察问题与期望：

- 在浏览模式搜索栏使用微软拼音或微信输入法输入中文时，候选阶段的 `Enter` 可能
  被 Muller 当作提交搜索，焦点随后离开输入框；候选阶段的 `Escape` 可能被当作
  清空搜索并使输入框失焦。
- 输入法仍在组合预编辑阶段时，中间拼音可能提前进入搜索，造成加载状态和结果
  跳动；最终中文上屏后又执行一次搜索。
- 输入法候选确认和取消只应影响本次组合输入，不应提交、清空或关闭 Muller 搜索，
  也不应切换结果焦点。
- 搜索只应在组合结束、最终文字确定后使用最终文字执行；当前目录、递归、全盘和
  双栏搜索都应遵守相同语义。
- 普通英文/数字输入、粘贴、`Ctrl+F` 聚焦以及非组合状态下的 `Enter`、`Escape`
  既有行为不得因此退化。

### 来源与上下文

- 来源：`用户上报`
- 提交人：`姓名未记录`
- 首次报告时间：`2026-08-24，具体时间未记录，时区为 Asia/Hong_Kong`
- 使用场景：Windows 用户在浏览模式中通过常驻搜索栏查找中文文件或文件夹，使用
  输入法候选窗完成中文组合输入。
- 附件：`None`

### 环境与复现

- 版本/提交：`feat/0.1.3，1563560`
- 系统与硬件：`Windows 桌面开发环境；Windows 具体版本、WebView2 版本、微软拼音版本、微信输入法版本和硬件未记录`
- 运行形态：`Muller Tauri/WebView2 前端；诊断补充使用真实 Vite 前端、Edge Chromium 和 Tauri 目录 mock`
- 前置条件：`进入浏览模式并聚焦“搜索当前目录”输入框；启用微软拼音或微信输入法，或按标准组合事件序列进行诊断模拟`
- 复现步骤：
  1. 在浏览模式中按 `Ctrl+F` 或点击搜索栏，使输入框获得焦点。
  2. 使用中文输入法开始输入拼音，并在候选文字确定前停留超过 120 ms。
  3. 按 `Enter` 确认候选，观察搜索请求、输入框焦点和结果列表焦点。
  4. 再次开始组合输入并按 `Escape` 取消候选，观察既有搜索词和输入框焦点。
- 实际结果：`标准组合事件模拟中，预编辑文本“zhong”先触发一次查询；组合态 Enter 后最终文字“中”虽然上屏，但焦点已移到目录列表并再次查询；组合态 Escape 会清空搜索并使输入框失焦。`
- 期望结果：`组合期间不消费候选键、不查询预编辑文本或切换焦点；组合结束后只使用最终文字进入既有搜索流程。`
- 复现频率：`标准 Chromium 组合事件模拟可稳定复现；用户已报告微软拼音和微信输入法适配不佳，但两款输入法的安装版复现频率尚未记录。`
- 证据边界：`当前运行时证据验证了 React 与 Chromium 的事件处理链，不等同于已完成微软拼音和微信输入法候选窗的 Tauri 安装版实机验收。`
