# Muller 软件设计文档

> 版本：v1.0 ｜ 日期：2026-07-20 ｜ 状态：设计定稿
> 定位：Windows 11 原生级重复文件清理 + 目录/文件差异比对工具，极致轻量与丝滑交互并重。

---

## 1. 概述

Muller 是一款面向开发者与重度文件管理用户的桌面工具，核心提供两大引擎：

- **去重引擎（De-duplication Engine）**：递进式三阶漏斗扫描，快速、安全地识别并清理重复文件。
- **差异比对引擎（Smart Diff Engine）**：目录级、文本级、二进制级三种粒度的差异比对。

设计原则：重计算全部下沉到 Rust 后端，前端只做可视化与交互；内存有界、任务结束即回落基线；所有破坏性操作默认可反悔。

### 1.1 优先级排序（决定一切取舍）

1. **性能**（最高，不可妥协）——目标 9/10 押在性能，仅 1/10 可让位于工程便利。
2. **流光视效 + 音效的实时性**——视效必须"零主线程成本"，音效触发 < 20ms。
3. **键盘驱动交互**——Emacs 风格方向键翻页、type-to-locate、可扩展快捷键。
4. **文件预览**。
5. 其余（框架、构建便利等）。

> 贯穿全文的性能铁律：**主线程只服务于列表滚动、键盘输入、音效触发**。任何视效（边框、粒子、光晕）一律赶出主线程——CSS 走合成器线程，Canvas 走 Web Worker。这是拿到 9/10 性能的前提，详见 §10。

## 3. 性能指标（修正后可承诺的版本）

| 指标 | 目标 | 备注（对原大纲的修正） |
|---|---|---|
| Rust 主进程常驻内存 | 空闲/最小化 < 15MB | **不含 WebView2 渲染进程** |
| WebView2 进程 | 前台约 40–100MB | 由系统 WebView2 决定，非本项目可压缩项 |
| 整进程树前台峰值 | 力求 < 150MB | 原"整机 20–30MB"不可实现，此处如实修正 |
| 哈希读缓冲 | 有界，数百 KB 量级，不随文件大小增长 | 原"<4KB"过小、吞吐差 |
| UI 滚动帧率 | 稳定跟随屏幕刷新率（含 144Hz） | 滚动时降级背景 shader |
| 音效触发延迟 | < 20ms | 走预解码 Web Audio，见 §6 |

> 内存哲学：不追求任务管理器上的"数字表演"。**明确不调用 `EmptyWorkingSet`/`SetProcessWorkingSetSize` 强制压缩工作集**——那只是把页换出到页文件，下次访问立即缺页换回，制造磁盘 I/O 与卡顿。真正的节流靠 Rust 所有权在任务结束时 drop 临时缓存，并可选启用 `mimalloc` 做堆 trim。

## 4. 系统架构

```
┌─────────────────────────────────────────────────────────┐
│  React 19 + Motion + React Bits (WebView2 渲染进程)       │
│  - 虚拟列表 (react-virtuoso)  - 弹性动画  - 预解码音效     │
└───────────────▲───────────────────────┬──────────────────┘
                │ ipc::Channel (分页流)  │ invoke (命令)
                │ 自定义协议 (字节流)     ▼
┌───────────────┴───────────────────────────────────────────┐
│  Tauri 2.x 桥接层                                          │
├────────────────────────────────────────────────────────────┤
│  Rust 后端                                                  │
│  ┌──────────────┐  ┌──────────────┐  ┌─────────────────┐  │
│  │ 去重引擎      │  │ 差异比对引擎  │  │ 资源守卫         │  │
│  │ (三阶漏斗)    │  │ (目录/文本/  │  │ (drop/挂起/     │  │
│  │              │  │  二进制)      │  │  路径拉黑)       │  │
│  └──────┬───────┘  └──────┬───────┘  └─────────────────┘  │
│         │  Tokio (遍历/IO)  +  Rayon/spawn_blocking (哈希)  │
└───────────────────────────┬────────────────────────────────┘
                            │ 命名管道 IPC（查询/结果流）
                ┌───────────▼────────────────────────┐
                │  Muller Indexer 服务（SYSTEM 权限） │
                │  读 MFT 建全盘索引 + 监听 USN 增量   │
                │  详见 §15.10 权限分离架构           │
                └─────────────────────────────────────┘
```

> **进程模型（因搜索路线 A 而定）**：上方 GUI + Rust 后端为**普通权限**进程（承载全部视效/交互/去重/比对）；下方为**独立的高权限索引服务**，专做 Everything 级 MFT+USN 全盘索引，经命名管道与 GUI 通信。权限分离的理由与细节见 §15.10。

### 4.1 线程与 I/O 分工（关键约束）

- **目录遍历、元数据读取、事件调度** → Tokio 异步任务。
- **文件哈希（CPU + 大块顺序 I/O）** → **Rayon 线程池**或 `tokio::task::spawn_blocking`。
- **严禁**把重哈希直接丢进 Tokio 的 async worker，会饿死 I/O 事件循环，导致前台掉帧。

### 4.2 IPC 策略

- 分页索引、扫描进度 → `tauri::ipc::Channel`（比反复 `emit` + JSON 序列化高效）。
- Hex/二进制字节段 → 注册**自定义协议**直接投喂字节流，避开 JSON 编解码。
- 前端**不在 JS 内存中维护深层文件树**，按需消费后端推送的分页数据。

## 5. 后端引擎设计（Rust）

### 5.1 去重引擎 · 递进式三阶漏斗

目标：以最小 I/O 代价把候选集逐级收窄，只对极少数最终候选做全量哈希。

**一阶 · Size Match**
- 并发遍历目标目录，仅读元数据（`metadata()`），按文件大小分桶。
- 大小唯一者直接排除。近乎零 I/O 成本。

**二阶 · Head/Tail Hash**
- 对同大小桶内文件，流式读取头部 + 尾部各 64KB（小文件读全量），用 **xxHash（或 BLAKE3 短哈希）** 算特征指纹。
- 排除约 90% 的伪重复。

**三阶 · Full BLAKE3 Stream**
- 对前两阶完全一致者，用 **Rayon 多核并行**流式读取，计算全量 **BLAKE3** 指纹。
- 有界缓冲边读边释放，单文件哈希期间内存占用不随文件体积增长。
- 选型说明：去重场景 BLAKE3 优于 SHA-256（多核吞吐更高、内建并行、抗碰撞足够）。是否用 `mmap`（`memmap2`）作为可选优化——**默认关闭**，因为海量小文件会撑爆地址空间、且文件被外部截断时可能 SIGBUS；顺序带缓冲 `Read` 通常同样快且更安全。

**安全防线**
- 删除默认走 **Windows 回收站**（`trash` crate），可反悔。
- 强制拉黑系统关键路径（`C:\Windows`、`C:\Program Files` 等）。
- 拦截并保护被系统独占的硬锁文件。

**分组数据结构**
```rust
struct DuplicateGroup {
    hash: Blake3Hash,
    total_size: u64,
    files: Vec<FileEntry>,   // 同组重复文件
    suggested_keep: usize,   // 建议保留项索引
}
```

### 5.2 差异比对引擎 · 三种粒度 + 就地编辑

能力级别：**比对 + 双侧就地编辑**（对标 Beyond Compare，含单向合并与直接编辑保存）。

**目录级 · Folder Diff**
- 两侧各构建 `HashMap<相对路径, FileMeta>`，按路径归类：
  - 仅左存在（暗红）／仅右存在（暗红）／双侧存在但有差异（暗黄）／完全相同（正常）。
- 差异判定分级：**以内容为准**——size 不同即判为差异；size 相同则比 BLAKE3（复用去重引擎哈希，见 §13）。
  - **mtime 不作为差异判据**，仅作提示：内容相同但 mtime 不同的文件标为"相同（时间戳不同）"，用小图标/角标区分，不刷成"有差异"。避免仅时间戳差异淹没真实差异。
  - 可选开关 `treat_mtime_as_diff`（默认关）：需要严格按时间戳区分时再开。
- **下钻**：双击"有差异"的文件对 → 按类型进入文本或 Hex 比对（流程见 §5.3）。
- 修正：不使用 Radix Tree。基数树是为共享前缀字符串键设计的，此处 HashMap 更简单更快。

**文本级 · Text Diff（双路线，按是否编辑分流）**
- 差分算法统一用后端 **`similar` crate（Myers）**，算行级 + 字符级区间。
- **只读/大文件路线**：后端算好差异，以 JSON 分页/增量流推前端**虚拟 Table** 渲染。百万行比对，计算完成内存回落基线。性能极致，用于"只看不改"。
- **编辑/合并路线**：前端 **CodeMirror 6 + `@codemirror/merge`** 双栏视图，左右栏可编辑、带 hunk 应用句柄。
  - 选型说明：这既满足"放弃 Monaco、极致轻量"（CM6 体积远小于 Monaco），又提供可编辑 + IME 支持。**中文输入法是决定性理由**——自研虚拟化 contenteditable 处理 IME 极痛苦，CM6 已解决。
- 两条路线共存：默认进只读高性能视图；用户点"编辑/合并"再挂载 CM6（懒加载，不进首屏 bundle）。

**二进制级 · Hex Diff**
- 非文本文件转 16 进制字节流双栏对齐（差异字节高亮）。
- 后端仅按需读取当前视图前后数百字节段落，绝不整文件载入。
- 字节段经自定义协议直投 webview。本期 Hex 为**只读**（就地改二进制风险高，不在本期范围）。

**文本 / 二进制判定 + 编码检测（中文关键）**
- 文本 vs 二进制：嗅探首 8KB 有无 NUL 字节及不可解码比例 → 决定走 Text 还是 Hex。
- 编码检测：`chardetng` + **BOM 嗅探**。注意 **UTF-16 必须靠 BOM 识别**（chardetng 本身不认 UTF-16）；GBK/UTF-16 中文文件是真实场景，须正确处理。
- 统一在后端解码为 UTF-8 后再 diff；保存时按**原编码 + 原行尾（CRLF/LF）**写回，不擅自转换。

> 拼写修正：原大纲 "Meyers" 应为 **Myers** 差分算法。

### 5.3 就地编辑与合并（后端接口 + 安全写回）

比对结果可直接编辑并保存，或把差异块从一侧合并到另一侧。核心难点是**写回安全**——用户真实文件不能损坏。

**数据结构**
```rust
enum DiffKind { Text, Binary }

struct FilePairMeta {
    left: PathBuf, right: PathBuf,
    left_enc: Encoding, right_enc: Encoding,   // 检测到的原编码
    left_eol: LineEnding, right_eol: LineEnding, // CRLF/LF，保存时保持
    kind: DiffKind,
}

struct Hunk { id: u32, left_range: LineRange, right_range: LineRange, changed: bool }
```

**Tauri 命令**
```rust
#[tauri::command] fn open_diff(left: PathBuf, right: PathBuf) -> FilePairMeta;
#[tauri::command] fn compute_text_diff(meta: FilePairMeta, on: Channel<DiffChunk>);
// 合并：把某侧 hunk 应用到另一侧（内存态，不立即落盘）
#[tauri::command] fn apply_hunk(session: SessionId, hunk_id: u32, dir: MergeDir);
// 保存：原子写回
#[tauri::command] fn save_side(session: SessionId, side: Side) -> Result<SaveReport, String>;
```

**安全写回（三重保护，破坏性操作的红线）**
1. **写前备份**：保存前把原文件复制进回收站（`trash`），可反悔。
2. **原子写**：写临时文件 → `fsync` → 原子 `rename` 覆盖，杜绝半截文件。
3. **外部改动检测**：`open_diff` 时记录 mtime + 哈希；`save_side` 前复核，若文件被外部进程改动 → **拒绝保存并提示**，防止无声覆盖他人修改。
4. 保存严格按 `FilePairMeta` 的**原编码 + 原行尾**编码，不擅自转换。

> 写回属破坏性操作：默认走回收站备份 + 原子写 + 冲突检测，任何一步失败即中止并如实报告，不留半成品。

### 5.4 差异导航（与键盘系统联动，§11）

- 差异块（hunk）导航是比对的高频操作，注册为命令，绑定方向键：
  - `next-diff` / `prev-diff`（默认 `Alt+↓ / Alt+↑`）跳到下/上一个差异块。
  - `apply-hunk-to-left` / `apply-hunk-to-right` 合并当前块。
  - `next-conflict`（若未来做三方合并）预留。
- 跳转后目标 hunk 居中并高亮，触发 §6.3 选择音效（受限流）。
- 与 §11 命令注册表统一：键位可在 keymap 里改。双栏**同步滚动**默认开启（左右按 hunk 对齐锁定），可关。

## 6. 前端设计（React 19）

### 6.1 视觉语言
- 窗口材质：Windows 11 **Mica Alt（云母）** 暗调，微弱透色 + 细腻噪点层。
- 动态光效：React Bits 流光边框 / 流体光晕 / 粒子扩散，仅用于"扫描完成""完美同步"等**瞬时**成功态。

#### 主色调（黑 + 紫色流光 + 蓝，对齐 React Bits 视觉）

设计令牌（CSS 变量集中定义于 `theme.css`）。**注意：除标注来源者外，以下为与 React Bits 暗紫蓝视觉一致的建议值，落地时以取色器对着官网 demo 校准**（校准方法见下）。

| 令牌 | 建议 hex | 角色 |
|---|---|---|
| `--bg-base` | `#0A0A0F` | 近黑主背景（Mica 之下的基色） |
| `--bg-elevated` | `#12121A` | 卡片/面板抬升面 |
| `--violet-core` | `#510679` | 紫流光核心色（**来源：React Bits Pro 实际用色**） |
| `--violet-glow` | `#7357CC` | 紫流光高亮/发光 |
| `--blue-accent` | `#1D2791` → `#3B82F6` | 蓝色强调（深蓝底 → 亮蓝点缀） |
| `--flow-gradient` | `linear/conic(紫 → 靛 → 蓝)` | 边框流光 / 光晕的渐变（`#8312A5 → #561496 → #1D2791`） |
| `--text-hi` | `#F5F5FA` | 高对比文字（当前目录等） |
| `--text-lo` | `#8A8A9A` | 低对比文字（上级目录等） |

- **流光边框（§10.4）取色**：`u_hue` 基准取 `--violet-core`↔`--blue-accent` 之间的色带；成功态偏暖不在此列，scanning 用青蓝，danger 用红。
- **校准方法**：本表为建议起点，非官方精确值。落地时对 [reactbits.dev](https://reactbits.dev) demo 用取色器取其背景/紫/蓝三点，覆盖上表变量即可；下游组件因只引用变量，无需逐个改。
- 无障碍：文字对比度须过 WCAG AA（`--text-hi` on `--bg-base` 已满足；`--text-lo` 仅用于非关键辅助信息）。
- 弹性物理：**所有会动的元素统一走 §6.5 弹簧系统**（弹窗、侧边栏、列表行、选择框、勾选、面板开合皆然），全站放弃线性/缓动过渡。

### 6.2 文件看板（Explorer Base）
- 多标签页 + 双栏对称（Dual-pane）布局，标签支持浏览器式拖拽拆分/合并。
- **虚拟滚动**：`react-virtuoso`，DOM 仅渲染可视区数十个节点，10 万文件不卡。
- 流式增量刷新：经 `ipc::Channel` 按需消费后端分页索引。

### 6.2.1 地址栏 · 层级焦点面包屑（缩放动画）

地址栏把当前路径按层级排开：**当前目录用大字号、上级目录递减小字号**，形成"当前在此"的焦点感。左右键（上/下级导航）时字号平滑放大/缩小过渡。

**布局与字号阶梯**
- 路径 `根 / … / 父 / 当前` 水平排列（超长首部折叠为 `…`，保留末几级）。
- 字号阶梯：当前级最大（如 22px），父级次之（16px），再上更小（13px），到基线为止。仅体现"焦点—次要"层次，非无限递减。
- 配色套 §6.1：当前级 `--text-hi`，上级 `--text-lo`。

**缩放动画（性能红线，必须按此实现）**
- **严禁用 spring/过渡动画 `font-size`**——它每帧触发 layout+paint，违反 §6.5 规则 2，连按左右键必卡。
- **正确做法：`transform: scale`**。每个层级节点**始终以其"最大态字号"渲染 DOM**（字形固定），再用 `scale` 缩到当前该有的大小。
  - 例：父级 DOM 以 22px 渲染，静止态 `scale(16/22)`；升为当前级时 `scale` 补间到 `1.0`。
  - **好处**：放大到当前级时是 `scale(1.0)` = 原生 22px 清晰字形，**不发虚**（先小字号再放大才会糊）。
- 过渡走 §6.5 弹簧系统：用 `snappy` × 全局回弹档 → 层级切换时带一点点回弹，与选择框手感统一。
- 只动 `transform`，配合 `will-change: transform`，收敛后即 `auto`。整条地址栏的缩放动画在合成器完成，主线程近乎零成本。

**导航联动**
- 左键=上级、右键=下级（键位在 §11 keymap 可改），触发时：字号阶梯整体平移一档 + 上述 scale 补间；同步触发 §10.4 边框方向语义（下级顺时针 / 上级逆时针）与 §6.3 音效，三者同源于同一导航事件 → 视/听/边框统一。

### 6.3 音效引擎（对原大纲的重要修正）

**架构决策：使用预解码 + Web Audio，而非 WASAPI + IPC。**

理由：
- Web Audio 的解码是**一次性**的——启动时把短音效 decode 成 `AudioBuffer`，之后播放走浏览器**专用音频线程**（非主 JS 线程），触发近乎零延迟。原大纲"浏览器线程延迟"的判断不成立。
- 若走 WASAPI，链路变为 React → IPC → Rust → WASAPI，**IPC 往返本身就可能吃掉 15ms 预算的大半**；WASAPI 共享模式缓冲本就在 ~10ms 量级，独占模式会锁死声卡，工具类应用不可用。
- 结论：低延迟路径恰恰是预解码 Web Audio。若未来确需后端出声，用 `rodio`/`cpal`（底层即 WASAPI），但须接受 IPC 成本。

**音效规格**：< 300ms、48kHz/16bit 干净无拖音短音频。

| 交互 | 音效 | 约束 |
|---|---|---|
| Hover | 低沉木质轻敲 | 频率限流，每秒最多 10 次，防重叠烦躁 |
| Select | 清脆"咔嗒" | 明确动作确认 |
| Action（删除/合并） | 释放感空气爆破短音 | 配合文件向内坍缩渐隐动画 |

### 6.4 GPU 争用治理（新增）
- React Bits 的流光/光晕/粒子多为 WebGL/canvas shader，与 144fps 虚拟列表滚动会抢 GPU。
- 策略：**滚动进行时暂停/降级常驻背景 shader**；成功态特效仅瞬时触发，不常驻。

### 6.5 统一弹簧动画系统（所有位移/缩放/透明度都走它）

原则：**凡是会动的元素，一律弹簧驱动，放弃线性/缓动过渡**——选择框、行高亮、勾选、面板开合、标签拖拽、hunk 跳转全部统一手感。但"到处撒 spring"会违反性能第一原则，故设计为**一个集中式系统**，不是每组件各跑一条循环。

#### 六条硬规则（违反即掉帧）

1. **单一集中调度器（single ticker）**：全站只有一条 `requestAnimationFrame` 主循环，统一推进所有活跃 spring。集中调度/批处理优于每组件各自 rAF（后者几十个框同动即压垮主线程）。Motion 已内建此机制，直接用其 `useSpring` / `animate`，不自己起循环。
2. **只动合成器友好属性**：spring 只驱动 `transform`（translate/scale）和 `opacity`。**严禁**用 spring 动 `top/left/width/height`（每帧触发 layout+paint，必卡）。选择框跟随/尺寸变化一律用 `transform`。
3. **可打断、从当前速度接管**：spring 未停时被新目标打断，必须**带着当前速度**重新起振，不得跳变或重置。快速连按方向键时这是"流畅"的核心——CSS transition 做不到，这正是用 spring 的理由。
4. **静止即退出**：spring 收敛（位移/速度低于阈值）后立即从 ticker 移除并 `will-change: auto`，不空转、不常占合成层。
5. **与滚动互斥采集**：spring 目标值的更新（如选择框跟随选中行）与 §11 键盘节流共用帧对齐机制，每帧最多提交一次目标，杜绝目标值洪水。
6. **尊重 `prefers-reduced-motion`**：开启时 spring 退化为极短或瞬时，保可用性与无障碍。

#### 三档语义预设（统一手感，避免每处手调参数）

**参数模型：`duration` + `bounce` 解耦**（关键）。用 Motion 的 `{ duration, bounce }` 而非裸 `stiffness/damping`——`duration` 单管快慢、`bounce` 单管回弹量，两者正交。这样"调回弹"不会连带改变速度，手感不乱。`bounce` 取值 0（不回弹）～ 1（强烈回弹）。

手感预设只定义**速度**（`duration`），回弹量由下面独立的三档 `bounce` 决定，二者组合：

| 手感预设 | `duration` 意向 | 用途 |
|---|---|---|
| `snappy` | 短（快、跟手） | **文件选择框跟随、行高亮、勾选** —— 高频交互 |
| `smooth` | 中 | 面板/侧边栏开合、标签拖拽、预览面板 |
| `expressive` | 略长 | 成功态、粒子等低频情感化反馈 |

#### 回弹三档（独立可调，全局旋钮）

回弹强度抽出为一个**全局设置**，用户/主题可切，不改速度：

| 回弹档 | `bounce` 意向 | 手感 |
|---|---|---|
| `subtle` | 低（~0.15） | 一点点回弹，几乎察觉不到，偏工具感 |
| `standard` | 中（~0.3，**默认**） | 明显但克制的一点点回弹——**当前基线** |
| `lively` | 高（~0.5） | 活泼有生命感的回弹 |

- 最终 spring = `手感预设(duration) × 回弹档(bounce)`。二者都集中定义于 `springPresets.ts`，组件只引名字。
- **默认基线**：文件选择框用 `snappy` × `standard` —— 快、跟手，落位时带一点点克制回弹（你要的效果）。用户可把全局回弹切到 `subtle`（纯工具感）或 `lively`（更活泼），选择框及全站随之统一变化。
- 高频交互（选择框连按）即便 `lively` 也不会失控：`duration` 短 + 规则 3 从当前速度接管，回弹被下一次输入自然吸收，不会累积成晃动。
- **文件选择框专门说明**：独立绝对定位层，spring 驱动 `transform: translate + scale` 追随选中行（FLIP：测量目标 rect → 只动 transform），绝不逐帧改 `top/height`。

#### 与音效的流畅联动（呼应"音效也要流畅"）

- **事件对齐，而非动画中途触发**：交互音效在**动作提交的那一帧**触发（如选中确定的瞬间），与 spring 起振同时开始，二者同源于同一事件 → 视听同步，无错位。
- **音效同样可打断/限流**：高频连按时，音效走 §6.3 的限流（Hover ≤10/s）并支持**快速淡出旧音、起新音**（voice stealing），避免尾音堆叠成噪。选择音短促（<150ms）以跟上 `snappy` 的节奏。
- **参数联动**：音量/音高可轻微随 spring 速度调制（动作越快、音越干脆），强化物理一致感。属可选增强，默认关闭以保稳定。

## 10. 视效架构（核心：分段流光边框是交互语言，全程全速）

> 本节是"性能优先 + 视效实时性"两大目标的交汇点，也是对 React Bits 直接使用方式的**关键重构**。
>
> **产品定位（P0）**：分段流光边框**不是装饰，是交互反馈语言**——滚动时如马路虚线滚动、进入下级目录顺时针涌动、返回上级逆时针回流。它直接关乎产品成败，因此**全程全速运行，任何情况下都不降级**。降级的是其它东西（见 §10.6），不是边框。

### 10.1 决策依据（为"边框全程全速"服务）

- 144Hz 下每帧预算仅 **6.94ms**；主线程要跑虚拟列表滚动、方向键翻页、type-to-locate、音效触发。→ 结论不是"砍边框"，而是**边框根本不占主线程**：它在 Web Worker 的 OffscreenCanvas 里独立渲染，与主线程的列表滚动**物理上不争同一线程**，因此二者可以同时全速。
- 关键几何选择：边框做成**沿窗口四边的一圈细环带**（screen-space ribbon），不是全屏 shader。填充率极低（只覆盖边缘几十像素宽），GPU 成本可忽略，这是"全速也不塌"的物理基础。
- **真正要盯的风险不是这圈流光，而是 Windows 11 Mica 半透明层的合成开销**——半透明区域越大、越常刷新，DWM 合成越贵。故：边框流光区域与 Mica 透明区**尽量不重叠**（边框走不透明描边带），见 §10.8。
- **决定性的性能收益来自"离开主线程"，而非 WebGPU vs WebGL2**。你的负载（一圈 ribbon + 成功态数千粒子）用 WebGL2 已吃满收益。→ **WebGL2 为基线，WebGPU 仅作可选升级**（WebView2 基于 Evergreen Chromium，WebGPU 可用，但不作为依赖）。

### 10.2 三层视效模型

| 层 | 用途 | 技术 | 运行线程 | 主线程成本 |
|---|---|---|---|---|
| **Tier 1** | 小范围装饰描边（按钮/卡片 hover） | CSS Houdini `@property` + `conic-gradient` | **合成器线程** | **零**（无重绘、无 JS） |
| **Tier 2** | **主边框：分段流光交互语言**（滚动/进出目录方向语义，全程全速） | WebGL2 ribbon shader in **OffscreenCanvas** | **Web Worker** | 仅在导航/状态切换时 postMessage 一个小事件 |
| **Tier 3** | 粒子扩散（成功态瞬时爆发） | 同 Tier 2 的 Worker canvas | **Web Worker** | 触发时一次 postMessage |

> 层级定位变化：**Tier 2 主边框升格为核心交互语言，是本产品的灵魂**；Tier 1 CSS 边框退为次要装饰（按钮/卡片级小描边），不再承担主边框职责。

### 10.3 Tier 1 — CSS 流光边框（替换 React Bits 边框）

原理：conic-gradient 作为伪元素背景，动画只改一个 Houdini 注册的 `<angle>` 自定义属性 → 浏览器在合成器线程旋转，**不触发重绘/重排**。这是性能天花板。

```css
@property --beam-angle {
  syntax: "<angle>";
  inherits: false;
  initial-value: 0deg;
}
.glow-border {
  --beam-angle: 0deg;
  border: 2px solid transparent;
  background:
    linear-gradient(var(--bg), var(--bg)) padding-box,
    conic-gradient(from var(--beam-angle),
      transparent 0turn, var(--accent) 0.15turn, transparent 0.3turn) border-box;
  animation: beam 4s linear infinite;
}
@keyframes beam { to { --beam-angle: 360deg; } }
```

> 注：Tier 1 仅用于按钮/卡片级小描边，与主边框（Tier 2）无关，**不随列表滚动暂停**。主边框的滚动/方向语义全部在 Tier 2 实现。

### 10.4 Tier 2 — 分段流光主边框（产品灵魂，重点展开）

主边框是一圈**沿窗口四边的 ribbon（细环带）**，上面跑一段段流光。所有动效由 shader 用**参数化时间/相位**生成，行为切换只改 uniform，**绝不重编译 shader**（重编译是卡顿元凶）。

#### 几何与渲染

- 一块**全窗口 OffscreenCanvas**，`transferControlToOffscreen()` 交给 Worker；`requestAnimationFrame` 渲染循环完全在 Worker 内，主线程零参与。
- 边框几何 = 沿四边的一条闭合带，参数化为**周长坐标 `s ∈ [0,1)`**（从左上角顺时针展开）。流光 = 在 `s` 上运动的一段段高亮包络。填充率极低 → 全速也不塌。

#### 分段流光模型（"一段段流光"）

沿周长分布 N 段流光，每段是一个高斯/平滑包络。核心 uniform：

| uniform | 含义 |
|---|---|
| `u_phase` | 全局相位，每帧按 `u_flowSpeed` 推进；**符号决定方向**（+顺时针 / −逆时针） |
| `u_flowSpeed` | 流动速度（滚动速度映射到这里） |
| `u_segCount` | 流光段数（虚线密度，如马路虚线） |
| `u_segLen` | 单段长度占比 |
| `u_hue / u_intensity` | 色相 / 强度 |
| `u_directionPulse` | 方向切换时注入的一次性强脉冲（进出目录用） |

片段着色本质：`brightness(s) = Σ envelope( frac(s·u_segCount − u_phase) )`，`u_phase` 增减即整圈流光顺/逆时针流动。

#### 交互 → 动效映射（本产品的交互语言）

| 交互 | 边框表现 | 驱动 |
|---|---|---|
| **列表滚动**（如马路虚线滚动） | 分段流光沿边匀速流动，速度随滚动速度联动 | `u_flowSpeed ← f(scrollVelocity)`，`u_phase` 持续推进 |
| **进入下级目录** | 整圈流光**顺时针**加速涌动 + 一次方向脉冲 | `u_phase` 正向、`u_directionPulse=1`，spring 回落 |
| **返回上级目录** | 整圈流光**逆时针**回流 + 一次方向脉冲 | `u_phase` 负向、`u_directionPulse=1` |
| scanning | 高频细密流光（段数↑速度↑），青色 | `u_segCount↑, u_flowSpeed↑, u_hue=青` |
| 去重命中 | 单段冷白闪掠过一圈 | 注入一个高亮段扫过 `s` |
| success/完美同步 | 暖金整圈涌动 + 触发 Tier 3 粒子 | `u_hue=金`，发 `burst` |
| danger/删除确认 | 暗红低频缓动 | `u_hue=红, u_flowSpeed↓` |

#### 深度映射（预留模块，P2，暂不实现）

> 目标：把"当前目录层级深度"可视化到边框上，让方向语义从"好看"进阶为"有用"——用户扫一眼边框就知道自己进得有多深。**本期仅预留接口与映射意图，不实现渲染逻辑。**

- 预留 uniform：`u_depth`（当前层级，0 = 根），`u_depthMax`（会话内最深，用于归一化）。
- 预留映射意图（实现时再定标定曲线）：

| 深度信号 | 候选边框表现 |
|---|---|
| 层级越深 | 流光段数 `u_segCount` 越密（或色相向冷偏移，`u_hue` 蓝移） |
| 到达根目录 | 段数最疏 / 归位基准色，给"到顶"的确定感 |
| 深度突变（跳转书签等） | 一次更强的方向脉冲，区别于逐级进出 |

- **接口占位**：导航事件已可携带 `depth` 字段（主线程 → Worker 协议中预留，见下），Worker 侧先接收但忽略。这样后续开启只需实现 shader 分支，协议不用改。
- **明确不做**：本期 shader 不读 `u_depth`；标定曲线、色带、是否用段数还是色相承载深度，全部留到 P2 决策。避免过早锁死视觉方案。

#### 主线程 → Worker 协议（关键：主线程近乎零负担）

```
主线程                                 Web Worker (OffscreenCanvas)
──────                                 ────────────────────────────
导航: nav.emit('enter', {depth})   →   target.dir = +1; directionPulse = 1
                                       // depth 字段已预留，本期 Worker 接收但忽略 (见深度映射 P2)
滚动: 每帧节流后发 scrollVelocity   →   target.flowSpeed = f(v)
                                       rAF loop:
                                         phase += flowSpeed * dir * dt
                                         uniforms = spring(uniforms, target)  // 平滑过渡
                                         gl.uniform*(...) ; gl.drawArrays()
```

- 主线程**只发"目标值/事件"**，不发每帧数据；相位推进与 spring 平滑全在 Worker 内。方向切换靠改 `dir` 符号 + 脉冲，视觉上顺滑反向而非硬切。
- 滚动速度采集在主线程做**帧对齐节流**（每帧最多一次 postMessage），与 §11.5 键盘节流同一机制，杜绝消息洪水。
- **音效联动**：进入/返回目录的方向脉冲，同步触发 §6.3 对应音效（顺/逆可用不同音色），强化体感。

### 10.5 Tier 3 — 粒子扩散

- 复用 Tier 2 的 Worker 与 canvas，避免第二个 GL 上下文。
- 粒子用**实例化绘制（instanced draw）** + GPU 端位置更新（transform feedback 或顶点着色器按时间推进），CPU 不逐粒子更新。
- 成功态触发：主线程发一个 `burst{origin, count}` 消息，Worker 生成一批、用完即弃（生命周期结束不占内存）。

### 10.6 降级策略（反转：边框永不降级，降级发生在别处）

> 上一版设计"滚动时降级边框"已废弃——因为滚动流光、进出目录方向语义本身就是核心交互反馈，最需要它时降级会直接毁掉体感。

- **主边框（Tier 2）全程全速，不降级**。它跑在独立 Worker，不与主线程滚动争线程，物理上可以共存全速。
- 若真出现帧预算紧张，**降级顺序**如下（边框永远最后）：
  1. 先降 Tier 3 粒子密度 / Mica 半透明刷新；
  2. 再降列表滚动的非关键装饰（阴影、hover 高亮）；
  3. **主边框流光最后才动，且只降分辨率/段数，绝不停**。
- **能力探测**：无 OffscreenCanvas/WebGL2 的极端环境，主边框回退为 Tier 1 CSS conic 旋转（能表达顺/逆时针，但无分段细节），功能语义不丢。
- **可选 WebGPU 路径**：粒子量级未来暴涨时可切 WebGPU 后端，接口对主线程不变。当前不实现，仅预留。

### 10.7 关于 SharedArrayBuffer（性能预留，非必需）

若后续需要主线程与 Worker 零拷贝共享大块视效状态，可启用 SharedArrayBuffer —— 需 Tauri 自定义协议响应头带 `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp` 达成跨源隔离。当前 postMessage 小事件已足够，**不引入**，仅记录路径。

### 10.8 真正的性能风险：Mica 合成开销（必须盯住）

边框流光本身很便宜；真正可能吃掉帧预算的是 **Windows 11 Mica 半透明层 + DWM 合成**：

- 半透明区域越大、刷新越频繁，DWM 每帧合成越贵，且这发生在**你控制不到的系统合成器**里。
- 对策：
  1. **边框流光带走不透明描边**，不叠在 Mica 透明区上，避免"半透明 × 高频动画"的最坏组合；
  2. Mica 仅用于**静态背景大面积**，动效区域（边框、粒子）用独立不透明图层；
  3. 若实测 Mica + 全速边框仍紧张，提供"降低背景材质"选项（Mica → 纯色/低透明），**优先牺牲背景，保边框**。
- **验收**：144Hz 下，列表滚动 + 边框全速流光 + 后台扫描三者同开，用 DevTools 看合成器/GPU 线程是否掉帧——这是本产品最关键的一条压测线。

## 11. 键盘驱动交互系统（Emacs 风格，可扩展）

> 目标：重度方向键翻页、type-to-locate（Windows 资源管理器的"打字即定位"）、以及可配置/可扩展的快捷键体系。

### 11.1 架构：三层解耦

```
KeyEvent → [1 键序解析器] → [2 命令派发器] → [3 命令注册表]
           keymap/chord      Command ID       行为实现
```

- **命令与按键分离**：所有操作先注册为具名 **Command**（如 `list.pageDown`、`dedup.deleteSelected`），按键只是绑定到 Command ID 的映射。用户改键、扩展键位都只动映射表，不碰实现。这是可扩展性的根基。
- **JSON/TOML keymap**：默认键位随包发布，用户覆盖存于配置文件，运行时合并。支持导出/导入键位方案。

### 11.2 Emacs 风格键序（chord sequence）

- 支持**前缀键 + 多段键序**（如 `Ctrl+X Ctrl+F`）与 modal/前缀状态机。
- 方向键为一等公民：`↑↓` 逐行、`PgUp/PgDn` 翻页、`Ctrl+↑↓` 跳区块、`Home/End` 首尾、`Ctrl+v/Alt+v` 上下翻屏（Emacs 习惯）。
- **键序缓冲显示**：底部状态栏实时回显已按前缀（如 `C-x-`），超时或匹配即清空。

### 11.3 Type-to-locate（打字即定位）

- 复刻资源管理器行为：列表聚焦时直接敲字符 → 增量匹配当前目录文件名前缀 → 跳转并高亮首个匹配。
- **在后端做匹配**：字符缓冲经 IPC 发给 Rust，在已建立的分页索引上做前缀/模糊匹配，返回目标行号 → 前端 `virtuoso.scrollToIndex`。避免前端持有全量文件名。
- 连续输入合并为一个搜索会话（可配置超时，默认 ~800ms 重置），支持 `Backspace` 退格修正。

### 11.4 与视效/音效联动

- 每次跳转触发 §6 的选择音效（受频率限流）。
- 翻页/跳转的滚动期间自动进入 `is-scrolling` 态（见 §10.6），暂停视效保帧。

### 11.5 性能约束

- 键盘事件在**捕获阶段**统一处理，避免 React 合成事件冒泡开销；高频方向键（长按连发）做**帧对齐节流**（每帧最多处理一次滚动位移），防止事件洪水压垮渲染。
- 派发器为纯查表 O(1)，不做正则/遍历。

## 12. 文件预览

### 12.1 分类型预览策略

| 类型 | 预览方式 | 性能约束 |
|---|---|---|
| 文本/代码 | 复用 §5.2 文本引擎，语法高亮走轻量 tokenizer（非 Monaco） | 仅读并渲染可视区，虚拟化 |
| 图片 | 后端解码缩略图 + 原图按需 | 走**自定义协议**直投字节流，不经 base64/JSON |
| 视频/音频 | 原生 `<video>/<audio>` + 自定义协议流式 | Range 请求，边下边播，不整载 |
| PDF/文档 | 首屏页渲染，按需翻页 | 分页读取 |
| 二进制/未知 | 复用 §5.2 Hex 视图 | 仅读视图窗口前后数百字节 |

### 12.2 关键设计

- **预览是旁路，不阻塞列表**：预览加载在独立异步任务，取消要即时（切换选中项立即 abort 上一个预览任务，`tokio::select!` + 取消令牌）。
- **缩略图缓存有界**：LRU 上限（如 200 项 / 固定字节预算），超限即 drop，符合内存哲学。
- **大文件保护**：超阈值（如图片 >50MP、文本 >单页）先出占位与"按需加载"提示，绝不盲目全载。
- 预览面板作为双栏布局的第三区，开合走 Motion Spring 动画。

## 13. 去重引擎 · 可落地接口设计（Rust）

### 13.1 核心数据结构

```rust
use std::path::PathBuf;

/// 单个文件条目，元数据阶段即填充，哈希按需补齐
pub struct FileEntry {
    pub path: PathBuf,
    pub size: u64,
    pub head_tail: Option<u64>,   // 二阶 xxHash 特征
    pub full: Option<[u8; 32]>,   // 三阶 BLAKE3 全量
    pub locked: bool,             // 被系统独占的硬锁文件
}

pub struct DuplicateGroup {
    pub full_hash: [u8; 32],
    pub size: u64,
    pub files: Vec<FileEntry>,
    pub suggested_keep: usize,    // 建议保留项（如最早/最短路径）
}

/// 扫描配置
pub struct ScanConfig {
    pub roots: Vec<PathBuf>,
    pub blacklist: Vec<PathBuf>,  // 默认含 C:\Windows 等，强制拉黑
    pub min_size: u64,            // 忽略过小文件
    pub use_recycle_bin: bool,    // 默认 true
}
```

### 13.2 三阶漏斗的线程边界（性能关键）

```rust
// 一阶 + 二阶特征读取：I/O 密集 → Tokio
async fn stage1_size_match(cfg: &ScanConfig, tx: &Channel<Progress>)
    -> HashMap<u64, Vec<FileEntry>>;      // 按 size 分桶，唯一者已排除

async fn stage2_head_tail(buckets: ...) -> Vec<Vec<FileEntry>>;
    // 每文件读 head+tail 各 64KB，xxHash，再分桶

// 三阶全量哈希：CPU + 大块顺序 I/O → 必须 Rayon / spawn_blocking
fn stage3_full_blake3(candidates: Vec<Vec<FileEntry>>) -> Vec<DuplicateGroup> {
    use rayon::prelude::*;
    candidates.par_iter()
        .flat_map(|bucket| hash_bucket_streaming(bucket)) // 有界缓冲流式
        .collect() // 分组
}
```

> **铁律重申**：stage3 **绝不**放进 Tokio async worker（会饿死 I/O 事件循环、拖垮前台帧率）。遍历/元数据用 Tokio，重哈希用 Rayon。

### 13.3 流式哈希（有界内存）

```rust
fn hash_file_streaming(path: &Path) -> io::Result<[u8; 32]> {
    let mut file = File::open(path)?;
    let mut hasher = blake3::Hasher::new();
    let mut buf = vec![0u8; 256 * 1024];   // 有界 256KB，不随文件增长
    loop {
        let n = file.read(&mut buf)?;
        if n == 0 { break; }
        hasher.update(&buf[..n]);           // 边读边喂，边释放
    }
    Ok(*hasher.finalize().as_bytes())
}
```

- 可选 `memmap2` 默认**关闭**（海量小文件撑爆地址空间、外部截断致 SIGBUS 风险；顺序读通常同样快且更安全）。

### 13.4 Tauri 命令与流式进度

## 14. 落地顺序建议

> 分段流光边框（§10.4）关乎产品成败，风险必须**前置暴露**——它是第一个技术尖峰，先做垂直切片验证可行性，再铺其余。

1. **【技术尖峰】分段流光主边框垂直切片**（§10.4）——OffscreenCanvas + Worker + WebGL2 ribbon shader，先只做：滚动联动流光、进入顺时针/返回逆时针方向语义。**这是最高风险项，第一个做**。验收：与一个占满主线程的假滚动列表并行，边框仍全速无卡。
2. **去重引擎后端**（§13）——纯 Rust + CLI 验证，把性能地基打实，可脱离 UI 独立压测。
3. **虚拟列表 + 键盘系统**（§6/§11）——命令注册表 + keymap 先行，方向键/type-to-locate 落地；把真实滚动速度接到边框 `u_flowSpeed`。
4. **IPC 流式打通**——`ipc::Channel` 接扫描进度到列表，扫描态驱动边框 scanning 动效。
5. **音效引擎**（§6.3）——预解码 Web Audio 接入交互事件，顺/逆导航配不同音色。
6. **差异比对（只读路线）**（§5.2）——目录 diff + 后端 `similar` 流式推虚拟 Table + 编码检测；下钻、差异导航。
7. **就地编辑 / 合并（可编辑路线）**（§5.3）——挂载 CodeMirror 6 merge，实现 hunk 应用 + 三重保护安全写回。**破坏性写回，须最后做且充分测试**。
8. **Tier 3 粒子 + 成功态**（§10.5）、**文件预览**（§12）。
9. **启动模型 + 模式化交互**（§15.1–15.6）——托盘常驻、全局唤起、首屏、Search/Command 模式、终端 `cd`、Tab 补全、功能列、Tab 流转。可与 3/4 并行推进（依赖命令注册表）。
10. **文件操作 / 右键菜单**（§15.8）——Everything 级基础文件操作，先接**遍历兜底**搜索（§15.10 降级路径），不阻塞 GUI 开发。
11. **Indexer 服务（路线 A）**（§15.9/15.10）——独立高权限服务：`ntfs-reader`/`usn-journal-rs` 读 MFT + 监听 USN，命名管道 IPC。**风险与工作量大，独立里程碑**；完成前 GUI 用遍历兜底，完成后无缝切瞬时索引。
12. **服务安装器 + 安全加固**（§15.11）——一次性提权注册服务、命名管道 ACL、只读查询接口。

> **预留（P2，本期不实现）**：边框深度映射（§10.4）——接口/协议字段已占位，Worker 接收即忽略。

> **架构注记**：搜索已定**路线 A**（§15.9），引入**权限分离双进程**（§15.10）。GUI 全程普通权限；索引服务独立高权限。二者可并行开发——GUI 先用遍历兜底，服务就绪后切换。

**总验收线**：144Hz 下，列表滚动 + 边框全速分段流光 + 后台扫描三者同开，合成器/GPU 线程不掉帧（§10.8）。边框在任何情况下不降级。

## 15. 外围交互与启动模型（Emacs 心智）

整体心智：**常驻后台 + 全局唤起 + 模式化按键 + M-x 式命令行**。用户几乎不用鼠标即可完成全流程。

### 15.1 快速启动 = 常驻，不是冷启动

- **开机自启到托盘**：`tauri-plugin-autostart` 注册开机启动，启动即隐藏到系统托盘常驻（不弹窗、不抢焦点）。
- **全局快捷键唤起**：`tauri-plugin-global-shortcut` 注册系统级热键（默认 `Alt+Space`，可改），按下即 `show()` 已存在的窗口 → 毫秒级出现。**关键：不是每次新建窗口，而是显隐一个常驻窗口**，这是"快速启动"的真正实现方式。
- 失焦自动隐藏（可配），再次唤起恢复上次状态。
- 呼应 §3 内存哲学：隐藏时走 §7 状态挂起（webview 挂起、特效暂停），托盘常驻内存压到最低。

### 15.2 首屏与"任意键进搜索"

- **首个界面 = 主页（Home）**，非搜索框。极简、居中，呈现主色调流光边框（§10）与入口提示。
- **首次搜索：敲任意可打印键一次**即从主页进入搜索态，并把该键作为搜索首字符（零门槛，不用先找输入框）。
- **后续搜索：标准键位** `Ctrl+F`（或 `/`，可配）显式进入搜索。区别于"首次任意键"——首屏是零门槛引导，进入应用后回归标准习惯。

### 15.3 模式化交互（modal，Emacs/Vim 式）

三种主模式，状态栏显示当前模式：

| 模式 | 进入 | 作用 |
|---|---|---|
| **Normal** | 默认 / `Esc` | 导航、方向键翻页、命令派发 |
| **Search** | 任意键（首次）/ `Ctrl+F` | 文件名检索输入 |
| **Command（终端）** | `Alt+X` | M-x 式命令行，支持 `cd` 等 |

- `Esc` 逐层退回 Normal，符合肌肉记忆。
- 模式切换本身触发 §6.3 轻音效 + §10 边框状态色变化，用户对"我在哪个模式"有视听感知。

### 15.4 终端模式（`Alt+X`，M-x 命令行）

- `Alt+X` 唤出底部命令行（类 Emacs `M-x` / VS Code 命令面板）。
- 支持**目录操作**：`cd <path>`、`cd ..`、`cd -`（上一目录）切换当前工作目录，联动地址栏（§6.2.1）与边框方向语义（§10.4）。
- 支持调用任意已注册 Command（§11.1 命令注册表），命令与文件操作同源。
- **Tab 补全**（见 §15.5），命令历史上下键回溯。

### 15.5 搜索框 / 命令行的 Tab 补全

- **Tab 补全**路径与命令：补全候选由**后端**基于当前目录索引计算（§13 已建索引/§15.7 搜索索引），前端不持有全量名单。
- 行为：Tab 补最长公共前缀；再 Tab 列候选；`Shift+Tab` 反向；候选列表用 §6.5 弹簧动画滑入。
- 补全候选命中触发 §6.3 选择音效（限流）。

```
│  功能列 (左)     │  文件结果列 (右, 虚拟滚动)         │
│                 │                                  │
│  [F2] 检索重复   │  name.ext        size   modified │
│  [F3] 文件比对   │  ...（react-virtuoso 虚拟渲染）   │
│  （可扩展）      │                                  │
└─────────────────┴──────────────────────────────────┘
      ⇄  Tab 在两列间跳转焦点
```

- **左列 = 功能列**，每项带快捷键标签，暂定：

| 功能 | 快捷键 | 关联 |
|---|---|---|
| 检索重复文件 | `F2` | §5.1 / §13 去重引擎 |
| 文件比对 | `F3` | §5.2 / §5.3 差异比对 |
| （预留可扩展） | — | 命令注册表新增即可显示 |

  - 功能列由命令注册表（§11.1）驱动，新增功能只需注册命令 + 声明快捷键，自动出现在列表，无需改布局代码。
- **Tab 流转**：选中文件时按一下 `Tab` → 焦点跳到另一列（功能列 ⇄ 结果列）。焦点转移用 §6.5 选择框弹簧动画平滑移动，配选择音效。`Shift+Tab` 反向。
- 焦点所在列有明确视觉指示（§10 边框局部高亮 / §6.5 选择框）。

### 15.7 搜索能力（关键岔路，见 §15.9）

- 搜索即时过滤结果列；输入经防抖后交后端匹配，前端只渲染可视区。
- 匹配在**后端索引**上做（前缀/子串/模糊），返回行号流 → 前端 `scrollToIndex`。
- **索引来源有两条技术路线，开发量与权限差异巨大 → 需决策（§15.9）**。

### 15.8 文件操作与右键菜单（对标 Everything）

选中文件后，**键盘可唤起右键菜单**（`菜单键` / `Shift+F10`，可配），也支持鼠标右键。提供最基础的文件操作：

| 操作 | 建议键位 | 说明 |
|---|---|---|
| 打开 | `Enter` | 默认程序打开 |
| 打开所在文件夹 | `Ctrl+Enter` | 定位到资源管理器 |
| 复制 / 剪切 / 粘贴 | `Ctrl+C/X/V` | 标准 |
| 复制完整路径 | `Ctrl+Shift+C` | Everything 常用 |
| 重命名 | `F2`（结果列内） | 就地编辑（注意与功能列 F2 按焦点区分） |
| 删除（到回收站） | `Delete` | 走 §5.3 回收站，可反悔 |
| 永久删除 | `Shift+Delete` | **二次确认**，破坏性 |
| 属性 | `Alt+Enter` | 系统属性对话框 |

- 右键菜单本身也是命令注册表的视图：项、键位、启用条件集中定义。
- 菜单弹出/关闭走 §6.5 弹簧动画；危险项（永久删除）视觉区分并强制确认，遵守破坏性操作红线。
- **焦点键位消歧**：同一物理键（如 `F2`）在不同焦点列含义不同（功能列=检索重复，结果列=重命名），由模式/焦点上下文路由，命令注册表按 `when` 条件区分。

### 15.9 搜索索引 = 路线 A（Everything 级 MFT + USN）【已定】

**决策：采用路线 A。** 本系统 Windows 专属，不为跨平台可能性牺牲核心搜索体验 → 直接吃满 NTFS 特性，做到 Everything 级全盘瞬时。

技术含义：直接读 **NTFS 主文件表（MFT）** 建全盘文件名索引（百万文件约 1 秒），挂 **USN 变更日志**做实时增量。现成 Rust crate 可用，不必从零解析：

- **[ntfs-reader](https://lib.rs/crates/ntfs-reader)** — MFT 枚举 + 缓存，有性能数据。
- **[usn-journal-rs](https://lib.rs/crates/usn-journal-rs)** — MFT + USN 的安全封装。
- **[ntfs (ColinFinck)](https://github.com/ColinFinck/ntfs)** — 底层 NTFS 结构，firmware 级到用户态。

### 15.10 权限分离架构（路线 A 的真正成本，必须如此）

读卷需要管理员权限，但**绝不能让整个 GUI 常驻进程提权运行**：UAC 每次开机弹窗；且高完整性级别进程**收不到普通 explorer 的拖放**（拖拽交互失效）。业界正解（Everything 同款）是**双进程 + 权限分离**：

```
┌────────────────────────────┐        ┌─────────────────────────────┐
│  Muller GUI（普通权限）     │  IPC   │  Muller Indexer 服务         │
│  - 托盘常驻、全局唤起        │◄──────►│  （Windows Service / SYSTEM）│
│  - 全部视效/音效/交互        │  本地   │  - 读 MFT 建全盘索引         │
│  - 拖拽正常（非高完整性）    │ 命名管道│  - 监听 USN 实时增量         │
│  - 查询索引、展示结果        │        │  - 维护索引，答查询          │
└────────────────────────────┘        └─────────────────────────────┘
        用户日常运行于此                   安装时一次性提权注册为服务
```

- **GUI 进程**：普通权限，承载你要的全部体验（视效、音效、键盘、拖拽）。绝不提权 → 无 UAC 骚扰、shell 交互正常。
- **索引服务**：Windows Service，以 SYSTEM/管理员运行，独占 MFT/USN 读取这一件事，开机自启。
- **IPC**：本地**命名管道**（named pipe），带访问控制；GUI 发查询、服务流式返回结果行号。查询协议与 §13 的 `ipc::Channel` 风格一致（流式、前端不持全量）。
- **安装**：服务注册需一次性管理员授权（安装器完成），此后日常运行 GUI 无需提权。
- **降级**：服务未安装/未运行时，GUI 回退为**按需遍历**（原路线 B 逻辑，即去重引擎 §13 的遍历），功能不残缺、只是非瞬时。→ 路线 B 不废弃，作为无服务时的兜底。

### 15.11 安全考量（新增服务面）

- **攻击面**：索引服务以高权限运行 + 暴露 IPC，是新增攻击面。命名管道必须设 ACL，仅允许本机当前用户连接；查询接口只读、不接受路径写操作。
- **最小权限**：服务只做索引，绝不代替 GUI 执行删除/移动等破坏性操作——那些仍由**普通权限 GUI** 执行（§15.8/§5.3），保持权限最小化。
- **数据边界**：索引仅含文件名/大小/时间戳等元数据（同 Everything），不读文件内容。
